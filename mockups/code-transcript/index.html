Sessions expire seconds after login on staging. Find out why and fix it.

  • Found the TTL written in seconds and read as milliseconds
  • Converted it once, where the config is read

Hook · after edit · prettier --write src/auth/session.ts · passed

SubagentExplore: the same mismatch outside src/auth

Scanned 214 files for TTL arithmetic

Found one more in src/cache/ttl.ts

Returned 1 finding to KLEIO

Fixed in both places, and the auth suite passes. The TTL was written in seconds and read as milliseconds, so a 30-minute session looked expired after 1.8 seconds.

What changed:

  • src/auth/session.ts converts the TTL to milliseconds once, where the config is read
    • issueSession() stores expiresAt in epoch milliseconds
    • isExpired() compares milliseconds with milliseconds
  • src/cache/ttl.ts had the same mismatch, which the subagent found. It’s fixed the same way, and both files now share one toMs() helper, so the two can’t drift apart again.

Before this ships:

  1. Run the full suite, not just auth.
  2. Log in on staging and leave the session idle past the 30-minute mark, to confirm it now lasts its full TTL; a frozen clock in the unit tests can’t show that.
  3. Merge behind the existing session-v2 flag.

@help is this a sound fix?

@help

Verdict: sound. The unit mismatch is the root cause, and both call sites now agree. One gap: no test checks the expiry boundary, so nothing stops this coming back.
