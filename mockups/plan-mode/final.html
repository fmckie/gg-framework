Rate-limit failed logins

Context

Failed logins aren’t counted today: POST /login checks the password and returns 401, so a script can try passwords as fast as the server answers. The only limiter, in src/http/limits.ts, guards signup.

Steps
  1. Move the limiter in src/http/limits.ts behind a createLimiter() helper that signup and login can share.
  2. In src/auth/login.ts, count failed attempts per account and per IP. After 5 failures on one account, or 50 from one IP, within 15 minutes, return 429 with a Retry-After header, so a script is slowed down without locking out someone who mistypes their password a few times.
  3. Reset an account’s count when it logs in successfully.
  4. Log each 429 with the account and the IP, so the limits can be tuned from real traffic.
  5. Add tests in src/auth/login.test.ts for the 5th and 6th failure, the reset and the header.
Files
  • src/http/limits.ts: the shared createLimiter()
  • src/auth/login.ts: the two counts and the 429
  • src/auth/login.test.ts: the new tests
Not in this plan
  • A CAPTCHA, or locking accounts
  • Changing signup’s existing limit
Risk

People behind one shared IP, such as an office or a VPN, share the per-IP count. That’s why its limit is 50, not 5.

Rollout

Ship behind the existing auth-v2 flag, with both limits read from config, so they can change without a deploy.
